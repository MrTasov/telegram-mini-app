## 1. Что сохраняем как направление игры

Сюжетная основа принимается из master plan: метеорит и развивающийся биоматериал, различие Monsters и Infected, учёный и его постепенно раскрывающиеся записи, загадочный Signal и его связь с Day X. Количество глав, конечная природа Signal и финальная разгадка **не фиксируются** этим техническим планом.

Основной цикл развития: восстановление базы → исследование мира → Research Data → запись/технология → новые возможности → подготовка к угрозе. Одновременно доступны короткая практическая задача, цель текущей сессии и более дальняя цель. Обязательные Objectives не должны превращать всю главу в сбор одного ресурса. Необязательные задачи и выбор улучшений сохраняют свободу.

Периметр остаётся узнаваемым и фиксированным. Бункер сохраняет роль безопасной производственной зоны. Свободно размещается ограниченное оборудование в допустимых местах; не все стены и помещения. Уничтожение обороны имеет последствия, но всегда остаётся путь восстановления. Главная история заканчивает сюжетную арку, а не сохранение и не саму игру.

Числа цен Lv.6–10, конкретная шкала Base Level/Threat и точный набор новых станций остаются предложениями. Многодневные реальные таймеры не входят в план.

## 3. Фундаментальные расширения и контракты

Ниже — предлагаемая архитектура, **не перечень уже существующих API**.

**Campaign/Chapters/Objectives.** Отдельный владелец недостающего состояния кампании, с доступом к фактам существующих owners. Definitions содержат стабильный ID, ключи RU/EN, зависимости, обязательность цели, тип условия и результат. Состояние хранит активную главу, прогресс и факт завершения/получения результата. Состояния главы: активна → обязательные цели выполнены → готова к переходу → переход подтверждён через Core. Выполнение цели не запускает следующую главу автоматически.

**Три семантики Objectives.** `Текущее состояние` — например, генератор работает сейчас; `достигнуто однажды` — питание впервые восстановлено; `действие после активации` — пережить будущую ночь или сдать исследовательские данные. Отдельно описывается потребление ресурсов: «имеет 10» и «сдал 10» не равны. Повторное повреждение стены не отменяет сюжетное открытие; предбоевой checklist может снова показывать необходимость ремонта.

**Общая проверка условий и доступности.** Один набор проверяемых условий используется Chapters, Research, Blueprints, recipes и upgrades. Он возвращает доступность и причину блокировки. Старые TECH IDs и уже выданные unlocks сохраняются. В этапе A новые исследования ещё не подменяют старые; позже оба пути подключаются к одной политике доступа. Ни DOM, ни открытая вкладка не являются источником unlock.

**Definitions → instances.** BuildableDefinition описывает тип, footprint, допустимые зоны, interaction anchors, доступ, профиль прочности/энергии и presentation assets. Instance хранит устойчивый ID, typeId, положение/поворот, scene/room, HP/уровень и ссылки на job/container/device. Стена сохраняет авторский section ID, станок получает отдельный instance ID. Одна сущность не должна одновременно жить в fixed fixture и во втором массиве placed objects.

**Команда → проверка → изменение → событие.** Новые операции получают actorId, target instance ID, request ID и ожидаемую ревизию там, где возможен конфликт. Владелец проверяет доступ, стоимость, расстояние/питание и существование объекта; изменение состояния и расход совершаются вместе. UI получает результат. Повтор команды не выдаёт награду и не списывает ресурсы дважды. Событие рассылается после изменения, не используется как единственное хранилище истории. Сейчас исполнение локальное; позже тот же контракт сможет исполнять сервер.

**Research/Blueprints/Archive/Sectors.** Это разные понятия: данные — найденный/сданный материал; Blueprint — право изготовить определённый тип; Research — выполненное исследование; Technology — результат/возможность; Log — открытая сюжетная запись; Sector — известность и доступность области. Граф связей проверяется на циклы и недостижимые обязательные узлы. Не делаем отдельный крупный «движок правил» для каждой категории.

**Threat и Base/Core progression.** Общие данные кампании; Threat читает подтверждённые milestones и состояние мира. Он не должен автоматически сводить на нет каждое улучшение игрока. Base Level — дополнительный агрегат развития, если его утвердим; Core Level — уровень конкретного аппарата. Не допускаем взаимного требования одного следующего уровня для получения другого.

## 5. Save System

Текущий `saveVersion=3` отличается от legacy `schema:2` и схем отдельных owners. Сохраняем существующие storage keys, идентичность слотов, backup/import/export и порядок validate-before-restore. Нельзя просто добавить `V010.register('chapters')`: список модулей сейчас закрыт. Новый owner подключается через явные GameSave adapters/обновлённый contract до `GameSave.seal`, с изменением `save/finalize.js` в нужном порядке.

При первом добавлении обязательного campaign state рекомендуется следующая версия envelope с миграцией; при неизменной базе это **3→4**, а не смена только номера release. Проверить также допустимые `gameVersion` в `save/slots.js`. Новая структура имеет собственную schema и content revision. Если формат не меняется, совместимость отсутствующих optional fields всё равно должна быть описана и протестирована явно.

| Слой | Новые сохраняемые данные |
| --- | --- |
| Campaign | profile/revision, Chapter и Objective state, переходы/полученные результаты, Research/Blueprint/Technology unlocks, сданные данные |
| Мир/база | Instance registry, wall state, positions/levels, общие containers, station jobs и power connections, Sector access, подтверждённый Threat/Base progress |
| Игрок | Носимые вещи, личный progress просмотра/intro, закреплённая цель; связывается с playerId |
| Не сохраняем | DOM, видео/изображения/AudioBuffer, текущие аудиоисточники, derived availability, временный placement preview, кэши маршрутов/рендера |

**Рекомендуемая политика старых saves — сохранить прогресс.** Не разрушать базу, не забирать станки/оружие, не сбрасывать день, HP, уровни, очереди, запасы и старые unlocks. Фиксированные объекты однократно отображаются в новые instances с предсказуемыми ID. Уже открытые возможности получают legacy entitlement, если новые сюжетные gates иначе их закроют. Не прятать уже посещённый доступный мир за новой обязательной главой.

Текущие факты можно признать: установленная станция, имеющийся уровень стены. Исторические события нельзя выдумать: найденный неизвестный Log, прежняя победа в сюжетной атаке, просмотр видео. Для них нужен явный путь присоединения старой базы к кампании без повторных starter rewards. Полный восстановительный сценарий — только новый слот/подтверждённый New Game.

Динамические objects проверять в два прохода: сначала записи instances и уникальность ID, затем ссылки job/container/device/priority по подготовленному индексу. Decode не должен временно регистрировать устройства в живом мире ради validation. После успешной проверки restore восстанавливает объекты и связи в явно заданном порядке. Удалённые/переименованные content IDs требуют migration/remap; неизвестный обязательный ID нельзя молча потерять.

Миграции проверять на повторяемость, отсутствие дублей, корректный отказ при неизвестной будущей версии и сохранение исходного слота при ошибке. Нынешний validate-before-restore **не гарантирует rollback при неожиданном исключении внутри restorer**. Новые restorers должны быть короткими присваиваниями подготовленных данных; внешние эффекты и награды исключить. Не выдавать существующий механизм за полноценную транзакционную БД.

Ещё одна граница для будущего сервера: некоторые существующие capture вызывают нормализацию предметов/турелей. Новые campaign/buildable snapshots проектировать без изменения мира; массовый рефакторинг старых capture не включать в первый патч.

## 6. Multiplayer readiness: предлагаемое владение

Это рекомендуемые решения для утверждения в первом этапе. Сервер, transport, matchmaking и сетевую игру сейчас не добавляем.

| Состояние | Предлагаемый владелец |
| --- | --- |
| Chapters, обязательные Objectives, Research/Blueprint unlocks, сданные данные, открытый Archive | Команда/кампания конкретного мира |
| Base/Core level, стены, постройки, Power/Fuel/Battery, общие склады и очереди | Общий мир |
| Day X, Threat, враги, ресурсы, доступ к Sector | Общий мир с одной authority |
| Research Drive до сдачи, bag/equipment, HP, движение и рабочее действие | Игрок с явным playerId |
| watched/unwatched, пропуск intro, pinned objective | Персональный progress игрока; unlock записи остаётся общим |
| Камера/масштаб/окна, RU/EN, субтитры, управление, громкость | Локальный клиент |
| Дрон/турель | Один объект мира; право командования — отдельное поле/правило |
| Fog-of-war | Сейчас смешан с настройками camera; рекомендуем общую разведку команды, личную камеру/метки. Точное правило sharing утвердить перед Sectors |

Поздно присоединившийся игрок получает открытые командой технологии и доступ к Archive, но не чужие личные отметки просмотра. Переход главы запускает уполномоченный игрок через Core; повторные запросы не запускают вторую главу. Правило host/голосование можно выбрать позже, оставив permission check уже сейчас.

Два запроса на одну площадку или один запас не должны оба успешно пройти после устаревшего preview: исполнитель перепроверяет placement, остаток материалов и revision. Контейнер адресуется ID, а не номером окна или текущим выбранным сундуком.

GameActors сейчас знает одного игрока; GameSimulation — локальный adapter, а не готовый сервер. Новые операции обязаны получать actor context, но переводить все старые подсистемы на co-op в этом плане не требуется. Новые случайные решения принимает authority; не менять старую Math.random/Cow Timer последовательность ради story patch. Для таймеров использовать simulation time/WorldClock, а не время воспроизведения ролика или локальные часы клиента.

## 7. Mobile Performance

Фактическая база для сравнения — сохранённые замеры Audio Pass: median **11,16 ms** на спокойной поверхности, **35,81 ms** при 100 zombies + 100 corpses, **25,99 ms** в бункере; audio observer median **0,105 ms** на отдельный вызов. Это native Canvas + моделируемые DOM/WebAudio на сервере, **не FPS телефона**. Уже тяжёлую сцену нельзя считать имеющей большой свободный бюджет.

- Objectives обновляются по событиям и изменившимся зависимостям. Не обходить весь граф/все объекты каждый кадр. UI обновлять только при изменениях и открытой панели.
- Placement preview использует локальный spatial query/footprint и кэш геометрии. Проверку проходимости выполнять ограниченно при изменении кандидата; final commit всегда повторно валидировать. Не запускать полный A* на каждый touchmove.
- Сохранить общий geometry revision и поэтапный pathfinding игрока/дрона. Перемещение ghost не инвалидирует реальную геометрию; committed placement/damage/repair обновляет её согласованно для навигации, видимости и стрельбы.
- Станции, power и audio получают один источник состояния/позиции. Считать allocation по изменению нагрузки/на существующем такте, не заново для каждого nav probe.
- Оборону/Threat ограничивать измеренными бюджетами активных объектов, врагов, projectiles, теней и audio voices. Сложность увеличивать составом/направлениями/поведением; не бесконечным количеством.
- Один video element и активный decoder, загрузка по запросу, внешний poster/субтитры; не preload всех Logs. Закрытие освобождает media и обработчики. Громкость/ducking согласованы с существующей Audio System.
- Сохранить sprite caches/atlases, culling и отсутствие новых больших base64. Контролировать размер save и стоимость сериализации: текущий ограничитель `SaveFormat.MAX_BYTES` равен 2 MiB; код проверяет длину JSON-строки, поэтому отдельно измерять и UTF-8 bytes.

Для каждого этапа: одинаковые сцены до/после, прогрев, несколько чередующихся замеров, median/p95, input latency, pathfinding slices, allocations/GC и память. По возможности один и тот же реальный телефон/Telegram. Конкретные лимиты объектов и допустимые дельты утверждать по измерениям устройства, не придумывать их из серверного FPS.

**A — безопаснее начать здесь.**

Добавить campaign definitions/state, три семантики Objectives, общую проверку условий, однократный переход главы, сохранение и минимальную панель Core с Chapters и сводкой Base. Одна небольшая проверяемая цепочка на существующих фактах; без наград, дублирующих старые GOALS. Старые Research/достижения остаются доступны через совместимый интерфейс. Новые вкладки показывать по готовности, не выдавать игроку шесть пустых экранов.

Затрагиваются progression, state/save, interaction/UI, локализация и command boundary. Главный риск — двойные владельцы unlocks/награды при restore. Тесты: condition semantics, duplicate command, готовность против перехода, сохранение/миграция, доступ при закрытом UI, cycle/unknown-ID checks. Вручную: понятна текущая цель, Core читается на телефоне, RU/EN, старый слот не теряет возможности. **HIGH:** общий campaign state и actor-addressed commands; никакого глобального currentPlayer внутри нового domain.

Физическое место Core выбирается после проверки центральной части бункера и путей; его footprint не должен перекрыть коридор/двери. Если подходящего готового asset нет, сначала отдельное утверждение визуала. В этапе A не отключать существующую базу и не применять повреждённый старт. Core может быть уже доступен в текущем мире; его сюжетное восстановление появится в C2.

**B — подготовка оборудования без свободной перестановки.**

Выделить тип и экземпляр фиксированных станций; один transform для renderer/collision/interaction/audio. Добавить адаптеры job/container/power по instance ID, сохранив прежние позиции, экземпляры и рецепты. Учитывать существующий feed_craft и upgrade0161; не считать их новыми станциями.

Затрагиваются manufacturing, power, rooms renderer, audio observer, save, inventory references и navigation geometry. Риски: двойной станок, потерянный output/refund, мощность от открытого окна, два save owners. Тесты: миграция активной/paused очереди и output, две изолированные instance-очереди одного типа в тестовом мире, ID uniqueness, равенство прежних координат/проходимости, save/load при power off. Вручную: все прежние станции, дверь рядом, дрон, звук из правильного места. **HIGH:** state станции общий, UI — только клиент; команды получают instanceId и actorId.

**C1 — подготовка восстановления и Power bootstrap.**

Расширить существующие wall/repair definitions, разделив стены и другие двери; определить protected/recoverable объекты. Подготовить New Game preset повреждений и оборудования, пока не применять к обычной новой игре. Проверить Tank, Generator, Battery, ручной доступ, Core и первые затраты.

Затрагиваются V015Base/V018Build, power, rooms, New Game factory и данные кампании. Риски: repair/production цикл, недоступное топливо, разрушенная опора/лестница, permanent softlock. Тесты: сценарий Generator off/Battery zero, все критические пути, уничтожение/repair одной секции, сохранение HP/level/repair credit, отсутствие влияния preset на старые slots. Вручную: можно дойти до каждого критического объекта и восстановиться минимальным доступным набором. **HIGH:** общий damage/repair и один атомарный расход, не привязанный к окну игрока.

**C2 — Chapter 1 как законченный игровой цикл.**

Только для New Game включить утверждённый preset: повреждения, частичная готовность комнат, стартовые доступы. Рекомендуемый порядок без тупика: стартовые инструкции/инструмент → Fuel/Tank/Generator → Core → доступная печь/материалы → критический ремонт → первая ночь. Точные стартовые количества и mandatory objectives утверждаются отдельно. Выполненные ранние действия учитываются до открытия Core.

Затрагиваются New Game/slots, Chapter definitions, Core/UI, ранние unlocks и стартовые объекты. Риски: случайно сломать Continue, недоступные обязательные ресурсы, повторный ввод/награда после reload. Тесты: весь путь из пустого слота, save/load на каждой ключевой границе, пропущенный/опережающий порядок действий, старый развитый мир, no-Power/no-space recovery. Вручную: понятен следующий шаг, запуск света ощущается событием, первая ночь достижима. **MEDIUM:** общий прогресс; личный tracker. Intro-видео добавляется в F; этот промежуточный этап не выдаётся за окончательный презентационный старт.

**D — ограниченное размещение станций в комнатах.**

Ввести placement zones, ghost, поворот, commit/cancel и небольшое число доступных типов. На старте допустим лимит одного экземпляра типа, заданный данными. Выбрать правила переноса занятой станции: безопасная первая версия запрещает перенос при job/output/refund; позднее перенос возможен только с сохранением всей сущности. Не превращать бункер в свободную фабрику.

Затрагиваются instance registry, craft/power/storage, collision/pathfinding, renderer, PC/touch controls. Риски: запертый выход, наложение, дублирование предмета при pack/move, нарушение маршрута дрона. Тесты: room/scene/footprint/interaction-clearance, стоимость, отмена, duplicate/stale command, save во всех состояниях, недоступная точка/длинное удержание пальца. Вручную: portrait/landscape, подтверждение без случайной установки, проход игрока и дрона. **HIGH:** preview клиента не является окончательной истиной; commit проверяет ревизию мира и доступную стоимость.

**E — Research Data и Blueprints.**

Добавить небольшой законченный цикл: гарантированно доступные данные → сдача через Core → исследование → один Blueprint/Technology unlock. Связать существующие улучшения Scout с отдельной веткой Drone Station: Battery, Durability, Ammo Capacity и Combat improvements. В этой же ветке предусмотреть Sensor Range и Charging Speed как будущие технологии; отсутствующие эффекты вводить отдельными небольшими поставками, не расширять весь дрон в этапе E. Сохранить четыре старых TECH и их результат; новые рецепты и разделение станций подключать к общей availability policy. Ориентир master plan — Smelter/Workbench/Weapon/Ammo/Medical; фактически сейчас оружие и патроны находятся в craft_bench, поэтому переносить категории и активные jobs только отдельными согласованными изменениями.

Затрагиваются progression, item/recipe definitions, inventory, Core, power и save. Риски: двойная сдача/расход, исчезнувший носитель, циклический gate, потеря старого рецепта. Тесты: AND/OR-зависимости, source доступность, pending results при полном bag, повтор заявки, нехватка power, миграция legacy unlocks/очередей. Вручную: понятно, что найдено, что требуется и что реально открылось. **HIGH:** носитель принадлежит actor до сдачи, принятые данные/результат — команде; списание и прогресс одной операцией.

**F — Archive, Video Log 01 и Intro.**

Добавить внешний 15–20-секундный Intro только для New Game, пропуск кнопкой/клавишей; первый Log открывается за Research. Archive хранит записи для повторного просмотра: Play/Pause/Skip/Close, RU/EN subtitles, watched/unwatched. Ошибка загрузки видео не блокирует главу; сохранить доступный текстовый/статический fallback. Сначала сценарий/раскадровка на утверждение, затем assets.

Затрагиваются MainMenu/session start, Asset Manifest/media loader, Audio System, I18n, Core Archive и персональный progress. Риски: autoplay/resume, лишние decoders, повтор Intro на Continue, потерянное управление после Close. Тесты: New/Continue различие, load error/Skip/Close/hidden/resume, один active media, освобождение ресурсов, сохранение flags без видео в save. Вручную: Telegram/iOS/Android насколько доступны, обе ориентации, читаемость субтитров, общий volume/mute. **MEDIUM:** Archive unlock общий, watched личный; просмотр одного игрока не определяет pause общего мира. В single-player допустима отдельная явная pause reason.

**G — Sectors и Exploration progression.**

Связать существующие регионы/known/discovered с data-driven Sector definitions: неизвестен, известен, доступен. Добавлять сигналы, обязательные источники данных и маршруты небольшими порциями. На первом шаге использовать текущую карту; новые большие территории и streaming не считать обязательной частью одного патча.

Затрагиваются world definitions, map/fog, loot/spawn, routes, progression и save. Риски: потеря доступа старого save, переход через обход gate, обязательный Drive в закрытой зоне, застревание при возвращении. Тесты: каждый обязательный sector достижим, reveal отличается от access, данные/маркеры не дублируются, старый player/drone/loot вне стартовой зоны сохраняется. Вручную: карта подсказывает направление без раскрытия всей истории; возвращение домой понятно. **HIGH:** доступ/источники данных общие; правила командной разведки и личных меток явно отделены.

**H — Surface Defense и последствия прорыва.**

На фиксированном периметре расширить размещение на допустимые внутренние площадки. Сначала один дополнительный defensive/support тип или одно расширение HMG. Добавить общий damage/repair/rebuild lifecycle, при необходимости power hook и взаимодействие с потерей опоры. Остальные Searchlights/Ammo Storage/Repair Modules/Drone Pads/Traps — отдельные контентные шаги после принятия основы.

Затрагиваются existing turret/build/health, world instances, damage targets, power, collision и saves. Риски: перекрытие маршрутов/спавнов, недоступный repair, уничтожение единственного выхода, предмет и установленная турель одновременно. Тесты: placement→damage→destroy→repair/rebuild→save/load, ammo/upgrade/identity conservation, safe recovery, пути и performance при нескольких сооружениях. Вручную: объект читается на телефоне, ясно повреждение/стоимость и как восстановить. **HIGH:** одна общая сущность; построить/починить/забрать — проверяемые команды с permissions и запретом двойного расхода.

**I1 — мировая активность боя отдельно от видимой сцены.**

Сначала определить, как база защищается, пока игрок находится в бункере или другом секторе. Сейчас некоторые enemy/turret update зависят от локальной scene и глобального player. Отделить вычисление активных боевых зон от отрисовки; использовать ограниченный бюджет симуляции, не запускать весь расширенный мир на полной частоте. Не добавлять в этом патче новые множители Threat.

Затрагиваются monster/turret tick, target context, GameFlow/world activity, navigation и save. Риски: невидимые мгновенные потери, двойной tick при смене сцены, остановка общего боя из-за UI/видео, лишняя CPU-нагрузка. Тесты: один и тот же налёт при player surface/bunker/другом секторе, переход во время боя, save/load, один damage/shot за событие, recovery после прорыва. Вручную: укрытие в бункере не выключает оборону; последствия понятны и не уничтожают прохождение. **HIGH:** боевые зоны принадлежат мировой authority; локальный render/camera не управляют их существованием. В будущем присутствие нескольких actors учитывается через явный контекст.

**I2 — Threat, Signal и разнообразие атак.**

Добавить bounded Threat state и определения состава/направлений атак. Расширять текущие siege/target selection: доступные стены, затем разрешённые defensive/support targets. Day X сохраняет прежний календарь. Signal сначала объясняет наблюдаемое поведение; окончательную природу не раскрывать.

Затрагиваются WorldEvents/Clock, enemy definitions/population/siege, структуры, audio/VFX и campaign. Риски: нарастающие повторные modifiers, бесконечные HP/численность, новая синхронная навигация для каждого врага, спираль поражений. Тесты: 9→10/00:00/05:59→06:00, save в событии, composition caps, потеря/смена target, недоступный target, расход и восстановление после поражения. Вручную: атака предсказуемо готовится, у разных улучшений есть польза, база восстанавливается после прорыва. **HIGH:** одна authority времени/спавна/выбора целей; local camera/video не запускают дополнительную атаку.

**J1 — Base/Core Level.**

После оценки реального темпа кампании выбрать, нужны ли обе шкалы, и определить требования по графу: Chapters, оборудование, Research, стены, ресурсы. Base Level не заменяет эти ветки и не служит единственным замком контента. Отдельная шкала остаётся необязательной: если её не утвердим, пропускаем её реализацию, а J2/J3 открываются через утверждённые Chapters/Research/Blueprints. J1 не превращает предложенную шкалу в обязательный технический барьер.

Затрагиваются campaign/unlocks, Core/instance upgrades, save/UI. Риски: циклы требований, автоматический откат после разрушения, повтор награды. Тесты: acyclic/reachable graph, next-level условия, duplicate request, повреждение ранее улучшенного объекта, миграция. Вручную: понятно, что уровень отражает и почему следующий закрыт. **HIGH:** командное достижение; заранее определить, что остаётся заработанным навсегда, а что проверяется как текущее состояние.

**J2 — Walls Lv.6–10 и экономика endgame.**

Расширять только утверждённые типы wall definitions; добавить читаемые визуальные ступени и полноценный эффект каждого уровня. Цены определять после измерения добычи/производства/ремонта и открытия более эффективных путей. Не копировать пример 200/400/800/1600/5000 как готовый баланс.

Затрагиваются health/upgrade definitions, economy, recipes/resource zones, assets и save validation. Риски: апгрейд всех дверей вместо стен, потеря HP/опор, бессмысленный grind, рост памяти теней/atlases. Тесты: каждый переход 5→6…9→10, HP/repair/cost, old levels, разрушенная секция/турель сверху, save/load и производственная пропускная способность. Вручную: визуальное усиление и реальный выбор между стеной, оружием, дроном и энергией. **HIGH:** общий upgrade target и один расход; новые способы добычи/переработки вводить отдельными balance patches, если объём вырастает.

**J3 — поздние типы и продолжение после истории.**

Heavy Combat Drone, advanced/heavy turrets, generator/power/equipment и новые enemies вводить по одному типу/ветке. Ветку Drone Station продолжать улучшениями батареи, прочности, боезапаса, сенсоров, скорости зарядки и боевой эффективности; существующие параметры переиспользовать, новые возможности вводить отдельно и измерять их эффект. Параллельно развивать сюжет небольшими главами/логами. Число глав определяется после полного progression graph. Финальная глава выставляет endgame unlock, не завершает симуляцию и не удаляет слот.

Затрагиваются соответствующие registries, progression, assets/audio, economy и saves. Риски: попытка одновременно изменить всё, бесполезность прежнего оружия, превышение active-object budget. Для каждой поставки — subtype compatibility, старые items/instances, бюджет популяции/боеприпасов/мощности, Day 100/200/500 и продолжение после финала. Вручную: новый тип имеет понятную роль, остаются короткие/средние цели и свобода вложений. **HIGH:** определения отдельно от instances, состояние общих объектов не копируется в каждого игрока.

## 9. Проверки и точки остановки

После каждого этапа: targeted tests изменённых контрактов, существующие затронутые suites, затем **один полный regression suite перед выдачей принятой сборки**, performance comparison и ручная PC/mobile/RU/EN проверка. Если после полного прогона исправлен локальный дефект, повторять затронутые группы; полный прогон повторять только при риске для общей симуляции/порядка инициализации. Не подменять исторические fixtures новыми ожиданиями ради зелёного результата.

Общие обязательные сценарии: старый save → migration → save/load; недоступное действие без частичного расхода; заполненный inventory; повторная команда/claim; power off; повреждение/потеря target; недоступная placement point; меню/hidden/resume; input на PC и multi-touch; GameAudio limits/loops; неизменный Day X; отсутствие progression deadlock. В контрактных тестах новые команды проверять с разными actor context без реализации сетевого транспорта.

Для первых этапов использовать существующие группы `saves`, `state-saves`, `differential`, `readiness`, `world-events`, `controls`, `localization`, `main-menu`, `world-farm`, `drone-return`, `resource-access`, `corrective-performance`, `audio-pass` и другие затронутые группы из `qa/run.cjs`. Новые проверки добавлять по поведению, а не по совпадению текста реализации.

Приёмка A отдельно: старый слот сохранён; Core/цели корректно отображаются и восстанавливаются; одно действие не засчитывается дважды; нет новых блокировок gameplay; код новых операций не зависит от локального UI. **Только после ручного принятия A обсуждаем и запускаем B.**
