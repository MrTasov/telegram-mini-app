# LAST BASE — Bunker Level 1 Rework

**Dependency audit + layout R1 для подтверждения. 23 сентября 2026.**

Предлагаю сохранить композицию присланного ориентира: большой центральный зал, три комнаты слева, три справа, одна жилая комната снизу, две отдельные лестницы рядом сверху. Все семь комнат выходят непосредственно в зал. Stage A и игровые системы Command Core сейчас не запускаются.

Это проект перестройки, а не реализованный патч. До изменения игры требуется подтверждение layout и описанного ниже режима сохранения временно недоступной фермы. Причина остановки — существенные ограничения, обнаруженные в существующей геометрии и save validation, и требование пункта 12 задания.

## 1. Проверенная исходная версия

Аудит выполнен на `LAST_BASE_0.29.0_Audio_Pass_Recovery_1`, сохранённой рабочей копии последнего Audio Pass. Все **947 файлов** совпали по SHA-256 с release manifest. Игровые исходники, собранный JavaScript, assets и пользовательские saves не изменялись.

Исходный ZIP: `LAST_BASE_0.29.0_Audio_Pass_Recovery_1.zip`, SHA-256 `438d2e75607235ca48280abbfebd196d22462a228297b3a8fba62f7b0ac28307`.

Помимо чтения исходников, в изолированном штатном QA runtime снят фактический реестр после всех переопределений функций: 53 bunker collision fixtures, 72 bunker interactions, 23 зарегистрированных power devices во всём проекте, 14 записей storage и 5 грядок. Ошибок инициализации runtime не было. Это снимок начального состояния тестовой игры, не анализ личного сохранения игрока.

Предыдущий Audio Pass имеет собственный результат **11 365 проверок / 38 групп / 0 ошибок**. В этой задаче suite повторно не запускался; эти числа не являются проверкой предлагаемой перестройки.

Центральный зал почти в **6,9 раза** больше отдельной комнаты по площади. Проёмы семи основных комнат — **160 единиц**, как у текущих боковых комнат. Комнаты не соединяются длинными коридорами. Существующий санузел остаётся внутренней частью жилой комнаты со своей дверью, а не восьмой функциональной комнатой.

Общий bounding box схемы — **2240 × 2240**. Это не сплошной квадрат пола: пространства снаружи стен закрыты. Размер боковых комнат сохраняется, а узкий коридор шириной 230 заменяется залом шириной 1200. Расширение происходит преимущественно вправо; три левые комнаты остаются на прежних координатах. Это сохраняет их рабочие пространства и сокращает объём переноса без искажения композиции картинки.

### Центральный объект

На этом этапе в центре предлагается **напольное обозначение места Command Core**, 360 × 280, координаты `(1030, 370)`. Оно не открывает меню, не выдаёт задания, не потребляет энергию и не имеет игровых функций. Сейчас обозначение проходимое, однако в расчёт доступности схемы консервативно включено как будущий твёрдый объект. Вокруг него предусмотрен свободный пояс не менее 120 единиц. Точки появления персонажей не попадают в будущий footprint Core.

Это именно резерв места: финальный sprite и возможности Command Core будут согласованы в Stage A. Оборудование по комнатам сейчас не размножается. Комната 05 целиком свободна, в остальных сохраняются существующие свободные участки. Ограничения будущего placement не реализуются в этом патче; проходы к дверям и оборудованию останутся доступными.

### Две лестницы

- **Левая: «НА ПОВЕРХНОСТЬ / EXIT UP».** Существующий переход на поверхность, с отдельной площадкой прибытия в зале `(1070, −120)`. Точка выхода на поверхности остаётся прежней. Четыре свободные позиции на площадке отмечены только как запас геометрии для будущих occupants; дополнительные игроки не создаются.
- **Правая: «УРОВЕНЬ 2 — ЗАКРЫТО / LEVEL 2 — LOCKED».** Отдельный визуальный лестничный пролёт за закрытым ограждением. Отдельная interaction сообщает о закрытом уровне. Не меняет scene, не загружает этаж и не открывает прежнюю ферму.
- Лестницы расположены рядом на краю центрального зала. Для перехода между направлениями не требуется обход комнат.
- Закрытый спуск не наследует состояние старой двери фермы и не становится доступным после ремонта, повреждения, отключения питания или загрузки save с разрушенными дверями. Это ограничение доступности этажа, а не новая строительная механика.

### Почему требуется подтверждение до перестройки

1. Новая геометрия существенно шире прежнего коридора: меняются navigation bounds, карту и свет нельзя оставить прежними.
2. Седьмая функциональная комната добавляет дверь и записи питания; простой перенос прямоугольников отклонит старые saves.
3. Недоступная ферма требует явного режима сохранения процессов. Скрыть только отрисовку недостаточно: животные действительно могут погибнуть.

Схема сохраняет композицию изображения. Технические изменения затрагивают общие привязки и загрузку состояния, поэтому сначала согласовываем эту конкретную R1.

## 5. Farm / Cows / Chickens — предлагаемая консервация

Предлагаю **временную паузу сельскохозяйственных процессов**, пока эта часть базы недоступна. Это необходимое исключение для сохранности существующего прогресса, а не изменение баланса фермы.

В текущем `updateLivestockProduction` вызываются питание и размножение; затем считаются яйца и молоко. `updateLivestockNeeds` расходует корм/воду и при длительной нехватке ставит `livestockAlive=false`. Эти вызовы не ограничены нахождением игрока непосредственно на ферме. `V011Farm.settle` вызывается также при capture и restore, а restore прибавляет offline growth. Поэтому одного пропуска draw/tick недостаточно.

Во время консервации:

- Сохраняются `farm`, `farmV011`, `farm014`, recovery/planting-stock flags, каждый plant elapsed/duration, irrigation phase/remainingMs/RNG, вода полива, harvestLeft.
- Сохраняются `livestock.animals`, существующие cow instance/stall IDs, reserve, nextCow, alive/warned/emptyMs, остатки production/breeding/needs timers. Уже погибшие в старом save животные не воскрешаются.
- Сохраняются **все 14** storage records и их содержимое. Основные 8 ящиков доступны в Level 1; 6 сельскохозяйственных записей остаются в состоянии. Их physical interactions из Level 1 отсутствуют. Явный расход через существующие общие источники материалов не переписывается.
- Рост, полив, расход корма/воды, голод, размножение, яйца/молоко и работа кормодробилки удерживают прогресс. Они не получают накопленный за время недоступности offline catch-up при следующей загрузке.
- Для кормодробилки сохраняются job, оставшееся время, queue, ready output, refunds и выбранные настройки. Пользовательский флаг pause не подменяется временным ограничением доступности.
- Скрытый контур не расходует мощность, но сохранённые room/device toggles и priorities не сбрасываются. На действующие приборы Level 1 консервация не распространяется.
- Dormant farm descriptors и старые save IDs остаются технически существующими. Нового scene `bunker2` и новой Farm Level сейчас нет.
- **Старый Cow Timer сохраняется отдельно от audible output**, включая прежние обращения к `Math.random` при одинаковых условиях работы таймера. Звук скрытых животных в Level 1 не проигрывается. Новая геометрия не использует gameplay RNG. Пауза размножения является намеренным удержанием сельскохозяйственного процесса; побитную идентичность всей симуляции работающей и законсервированной фермы не обещаем.

Консервация должна действовать на уровне владельцев состояния, включая capture/restore, а не через паузу всей игры. Временные поля записываются через существующий Save Pipeline. Выход из консервации будет частью отдельного согласованного Level 2 patch.

## 6. Безопасная миграция saves

Предлагаемый порядок реализации:

1. Добавить именованную однократную layout migration в существующую цепочку SaveFormat; исходная envelope version сейчас 3. Следующую ревизию формата и точную версию патча зафиксировать при реализации. Root payload schema и существующие owners сохраняются.
2. Работать сначала с копией разобранных данных. Валидировать исходные inventory, equipment, storage, farm, livestock, production и drone ownership; не применять частично неподтверждённые данные к живому миру.
3. Сохранять старые circuit/device/door IDs. Добавить defaults только для действительно новой резервной комнаты в известных старых версиях, до строгой проверки состава реестров. Не принимать неполный повреждённый новый save как legacy.
4. У relocated doors сохранить HP, level, manual/open/away. Сохранить также неактивную старую farm door и её данные. Locked Level 2 не заимствует ни её ID, ни HP.
5. Переносить позиции по известной старой зоне: left rooms без сдвига; energy/storage/living — согласно таблице; коридор — в соответствующую часть зала. Поверхность и её координаты не меняются. Положение из старой фермы проверяется только относительно активного Level 1, без доступа к dormant geometry.
6. Проверить player, flying/returning/disabled drone и guard target против финальных colliders. Для неверной точки выбрать ближайшую безопасную позицию в допустимой связной области, за пределами лестничных triggers и будущего footprint Core. Не возвращать сущность в скрытую ферму. Только если подходящей ближайшей точки нет — проверенная площадка входа.
7. `docked` drone перемещается на новую docking point; `packed` остаётся в том же контейнере с тем же token/instance ID. Battery/HP/ammo/modules/cargo не лечатся и не обнуляются. Закрытая дверь без питания сама по себе не повод телепортировать исправно расположенный drone.
8. Сбросить временный route/search, cache привязанный к прежней geometry revision и временный interaction target. Мигрировать сохранённые map goals / markers активных помещений; метки старой фермы сохранять как отложенные данные без активного маршрута Level 1. Имена пользовательских меток не терять.
9. Проверить позицию после восстановления всех door HP, power и geometry owners. Согласованно обновить камеру, collision/path caches, lights и mini-map. Учитывать sealed adapter order в `save/finalize.js`.
10. Повторная save/load не должна повторно сдвигать координаты. Новая игра использует тот же Level 1, но не применяет к новым позициям legacy offsets.

Недостаточно текущего entrance fallback: он чинит player по прежним предположениям и не покрывает свободно летающий drone. Предлагаемое решение должно быть общим геометрическим resolver с явными actor/radius/scene, а не двумя разными наборами координат.

## 7. Multiplayer readiness

Геометрия общая для всех actors. Фиксированные ID комнат/дверей/лестниц/оборудования не выводятся из имени игрока и не зависят от порядка в массиве игроков. Новые функции выбора безопасной позиции принимают радиус, scene и занятые позиции; вход не содержит правила «существует только один player».

Для automatic doors и запрета закрытия учитывается коллекция occupants из существующей actor boundary плюс drone. На площадке входа зарезервированы четыре свободные позиции; это геометрическая проверка будущего co-op, не работающая сетевая игра. Individual inventory и общий Power/Storage не копируются. Новый transport, authority server, shared missions или multiplayer save schema не создаются.

## 8. Performance и границы текущей проверки

Предлагаемая карта шире исходной. При шаге существующего path grid 12 единиц bounding grid вырастает с `126 × 184 = 23 184` до `187 × 187 = 34 969` ячеек, примерно **+51%**. Это оценка массива сетки, **не измеренное увеличение CPU или FPS-регрессия**. Поэтому обязательно измерить сложные маршруты после реализации, сохранив текущие slices и cache. Глобальный поиск на каждом touchmove не добавляется.

Большой hall mask при scale 0.5 потребует больше площади, чем старый corridor mask; исключение скрытой farm mask уменьшит часть нагрузки. Предварительно обещать улучшение FPS нельзя. Проверяется реальная суммарная память mask/cache и активных звуков, а не только число комнат.

На этом этапе выполнена только отдельная проверка предложенных прямоугольников: grid 12, radius 10, открытые двери, будущий footprint Core как твёрдое препятствие. Она проверяет связность помещений, площадку входа, кандидаты подхода к 18 функциональным targets, доступность выхода вверх и недоступность нижнего пролёта. Результат: **32 проверки, 0 ошибок**, записан в `LAST_BASE_Bunker_L1_Layout_Checks.json`.

Эта модель **не проверяет** анимированные door panels, настоящий runtime interaction line-of-sight, текущий A*, audio positioning на слух, загрузку мигрированных saves и реальный телефон. Такие проверки выполняются после согласования layout и реализации.
